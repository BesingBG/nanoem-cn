==========================================
nanoem 技术说明
==========================================

.. important::
    如果只是使用 nanoem，完全没有必要阅读本文档。本文档是为打算阅读 nanoem 源代码的工程师编写的。

.. warning::
    整个代码至少有 10 万行以上，阅读理解难度相当于阅读游戏程序或小型游戏引擎。
    当然，还需要理解 MMD/MME，此外还有不少依赖库，至少需要对它们有基本了解。

本文档说明 nanoem 源代码的构成。

大致上 nanoem 分为两个组件：

  * nanoem
  * emapp

此外还有为每个操作系统实现的 UI 层和汇总了依赖库的 ``dependencies``，
本文档主要围绕 ``nanoem`` 和 ``emapp`` 进行说明。

nanoem 的源代码在 `GitHub 上公开 <https://github.com/hkrn/nanoem>`_。

nanoem
******************************************

使用 C 语言编写的专注于 PMD/PMX/VMD 数据操作的库。严格意义上的 nanoem 指的是这一部分。
此外还附带以下扩展：

* 可变数据操作
* 文字转码 (CoreFoundation/ICU/Win32/Qt)
* PMM 数据操作
* NMD 数据操作
* 物理运算
* PMD -> PMX 转换
* JSON

nanoem 的 API 参考 CoreFoundation 的 API 设计，原则上提供不可变的 API。
此外，所有对象（结构体）均作为无法直接访问成员的不透明类型处理。
以此确保 ABI 兼容性。

对象大致分为 ``Model`` 和 ``Motion``， ``Model`` 可读取 PMD/PMX 两种格式，
但 emapp 侧实现会将 PMD 通过扩展提供的转换功能转换为 PMX 后再处理。
``Motion`` 仅支持 VMD，但通过扩展函数也可读取 NMD。两者具有相同的接口。

使用作为扩展提供的可变数据操作，可以直接写入不可变对象来修改数据。
不仅可以修改数据，还可以写入可写的缓冲区对象。
可变对象必须仅用于一个不可变对象。

对象层级
==========================================

* ``Model``

  * ``Vertex``

    * 顶点

  * ``Material``

    * 材质或材质

  * ``Bone``

    * 骨骼

  * ``Constraint``

    * IK
    * 注意与 BulletPhysics 的 ``btConstraint`` 不同
    * 其下有对应于 IK 链接的 ``ConstraintJoint``

  * ``Morph``

    * 变形或表情

      * ``BoneMorph``

        * 骨骼变形

      * ``GroupMorph``

        * 组变形

      * ``FlipMorph``

        * 翻转变形

      * ``ImpulseMorph``

        * 脉冲变形

      * ``MaterialMorph``

        * 材质变形

      * ``UVMorph``

        * UV 变形

      * ``VertexMorph``

        * 顶点变形

  * ``Label``

    * 分类

  * ``RigidBody``

    * 刚体
    * 对应于 BulletPhysics 的 ``btRigidBody``

  * ``Joint``

    * 关节
    * 对应于 BulletPhysics 的 ``btConstraint``

  * ``SoftBody``

    * 软体
    * 对应于 BulletPhysics 的 ``btSoftBody``

* ``Motion``

  * ``AccessoryKeyframe``

    * 配件的关键帧
    * 仅 NMD，VMD 不支持

  * ``BoneKeyframe``

    * 骨骼的关键帧
    * NMD 中进一步包含物理运算的切换信息

  * ``CameraKeyframe``

    * 相机的关键帧

  * ``LightKeyframe``

    * 照明的关键帧

  * ``ModelKeyframe``

    * 模型的关键帧
    * NMD 中进一步包含外部父级等信息

  * ``MorphKeyframe``

    * 变形的关键帧

  * ``SelfShadowKeyframe``

    * 自身阴影的关键帧

关于 NMD
==========================================

NMD 是 VMD 的向上兼容扩展，是基于 protobuf 的二进制数据。

* 对骨骼及变形名称没有限制

  * VMD 需要控制在 15 字节以内

* 与 VMD 相比通常可减少 10% 以上

  * 因为名称以数值 ID 方式管理

VMD 数据可以直接保存为 NMD。虽然 NMD 也可保存为 VMD，但
NMD 独有的扩展信息将会丢失。

数据规范定义在 ``nanoem/proto/motion.proto`` 中。

关于错误
==========================================

使用表示状态的枚举类型。可能发生错误的函数必须将该枚举作为函数的最后一个参数。

关于自定义分配器
==========================================

nanoem 内置了可替换为自定义分配器的功能，nanoem 内部必须通过自定义分配器进行内存分配和释放。
emapp 利用该自定义分配器检查内存泄漏。

关于字符串
==========================================

由于需要处理 ShiftJIS/UTF-8/UTF-16 编码，字符串作为独立的对象处理。
虽然提供了字符串转换的附加功能，但这实际上是必需的。

通过字符串工厂对象使用专用函数与字符串对象进行交互。

关于用户对象
==========================================

每个对象都有一个可绑定到任意对象的用户对象。
通常用户对象不会干预任意对象，但当对象的析构函数被调用时，
会在该时机销毁任意对象。

在 emapp 中， ``Model`` 对象利用这一机制持有扩展数据。
而 ``Motion`` 对象没有使用该功能。

nanoem 的实现策略
==========================================

* 仅使用空格，缩进为 4

  * 在 ``.editorconfig`` 中定义

* 基于 C89

  * 变量定义在函数开头进行

* 对应对象的结构体均为 opaque

  * 结构体的成员访问必须通过函数进行
  * 禁止直接公开成员

* 命名规则基于 OpenCL 的自定义规则

  * 结构体名称为 ``lower_snake_case``
  * 函数名以 nanoem 开头，使用 ``UpperCamelCase``
  * 常量为 ``UPPER_SNAKE_CASE``

emapp
******************************************

使用 C++ 编写的应用程序核心库。nanoem 的大部分处理都集中在这里。
设计上以 nanoem 和 emapp 为基础，将各平台的 UI 分离到 UI 层。

* emapp 出于历史原因，除了 C++ 异常、RTTI 及 C++11 的部分功能 (nullptr) 外，不使用其他 C++ 特性

  * 参见 :ref:`1BF7070C-25E0-4E04-B314-6C67FE55E6AB`
  * 由于也不使用共享指针或自动指针，需要严格管理指针

* 由于依赖库的关系，需要支持 C++14 的编译器

生命周期
==========================================

emapp 的生命周期与游戏或游戏引擎较为相似。

* 应用程序初始化

  * 初始化各种库
  * 创建项目
  * 检查上次是否发生崩溃，询问是否运行恢复处理

    * 用户接受时执行恢复处理

* 在应用程序结束被调用之前进行帧处理

  * 渲染处理

    * 渲染阴影贴图
    * 渲染效果的离屏渲染目标
    * 渲染视口

      * 为 ScriptExternal 渲染模型或配件
      * 渲染背景视频
      * 渲染网格
      * 渲染预处理效果
      * 渲染所有模型的边缘
      * 渲染所有模型及配件
      * 渲染所有模型及配件的地面阴影
      * 渲染后期处理效果
      * 转写 screen.bmp 专用的渲染目标

    * 批量处理渲染命令

      * 从 31.0 引入
      * 详见「批量处理渲染命令」项目

    * 渲染 UI 图标等
    * 渲染 UI (ImGui)
    * 在窗口中显示渲染结果
    * 如果请求了重置处理，执行重置处理

      * 重新生成并重新设置所有效果的所有渲染目标
      * 重新生成并重新设置视口的渲染目标

    * 每 2 帧向 UI 线程发送一次虚拟事件
    * 视频编码处理

      * 仅在视频编码处理执行中时

    * 项目更新处理

      * 更新音源位置

        * 仅音源播放中时

      * 定位处理

        * 物理运算前的运动应用处理

          * 对所有模型按以下顺序执行

            * 应用模型（显示和 IK 启用/禁用）的关键帧
            * 重置模型的材质
            * 重置模型的骨骼变形
            * 重置模型的变形
            * 应用变形的关键帧
            * 应用物理运算前的骨骼关键帧
            * 按骨骼关键帧切换物理运算的启用/禁用
            * 设置用于物理运算的骨骼参数

        * 执行物理运算
        * 物理运算后的运动应用处理

          * 对所有模型应用物理运算后的骨骼关键帧
          * 对所有配件应用关键帧
          * 应用相机的关键帧
          * 应用照明的关键帧
          * 应用自身阴影的关键帧

        * 更新相机
        * 更新照明

      * 模型变形处理

  * 各种事件处理

    * 事件处理中发生错误时显示错误对话框

  * 如果事件处理中请求了重置处理，再次执行重置处理

* 应用程序结束

  * 销毁项目
  * 结束各种库的处理

------------------------------------------

统一管理项目、渲染、UI (ImGui)、输入的对象。
通过 ``emapp::BaseApplicationClient`` 处理。

对应的 ``emapp::BaseApplicationService``

统一管理所有模型、运动、配件、效果的对象。

对应的 ``emapp::Project``

模型
------------------------------------------

对应于 PMD/PMX 的渲染对象。

对应的 ``emapp::Model``

配件
------------------------------------------

对应于 X 格式的渲染对象。

对应的 ``emapp::Accessory``

------------------------------------------

定义动作的对象。有以下类型，仅属于其中一种：

* 模型
* 配件
* 相机
* 照明

对应的 ``emapp::Motion``

相机
------------------------------------------

对应的 ``emapp::ICamera``

对应的 ``emapp::effect::Pass``

命令
------------------------------------------

可撤销的操作单位。作为 undo.c 的用户数据保存，通过 undo.c 的回调执行撤销或重做。
此外，利用 undo.c 的持久化机制，命令也具备在应用程序崩溃时撤销到上一次操作的能力。

关键帧的注册或删除、骨骼移动、变形更改等主要操作均通过命令执行。

还有可以将多个命令合并为一个的批处理命令，用于发生大规模关键帧更改的命令。

批量处理渲染命令
==========================================

到 30.0 为止，渲染命令是按材质或渲染目标逐条发出的，但在 Apple Silicon 支持中发现渲染崩塌的问题，
因此重新设计了渲染处理，按渲染目标汇总渲染通道。这样避免了不必要的渲染通道，从而提升了性能。

* ``Project::SerialDrawQueue``

  * 原则上每次发出渲染通道
  * 例外情况：如果上一次也是 SerialDrawQueue 且为同一渲染通道，且可合并则合并
  * 主要用于后期效果

* ``Project::BatchDrawQueue``

  * 按渲染通道汇总
  * 传统渲染基本使用此类

批量处理渲染命令对象的管理在 Project 中，但通过接口 ``emapp::sg::PassBlock::IDrawQueue`` 访问，因此内部不直接公开。

音源同步校正处理
==========================================

Windows 版和 macOS 版实现了比较音源位置和时钟偏移、优先选择延迟较小的同步校正处理。具体流程如下：

* 将音源位置作为采样偏移计算并获取
* 将时钟转换为秒并与音源频率相乘，作为采样偏移进行比较
* 将上述两者的差值作为延迟获取，与阈值（音源频率以 60FPS 为基准，Windows 版以 15FPS、macOS 版以 10FPS 计算）比较

  * 延迟小于阈值时采用时钟
  * 延迟大于阈值时采用音源位置

通常采用时钟，但在丢帧导致处理跟不上时，会强制采用音源位置。

emapp 的实现策略
==========================================

* 仅使用空格，缩进为 4

  * 在 ``.editorconfig`` 中定义

* 禁止使用 C++ 异常
* 禁止使用 C++ 运行时类型信息 (RTTI)
* 除 C++11 的 ``nullptr`` 外禁止使用其他 C++11 特性

  * 但 UI 层可例外使用 C++11
  * UI 层也不允许使用 C++14 及之后的特性

* 原则上不使用 STL

  * 改用附带的 `TinySTL <https://github.com/mendsley/tinystl>`_
  * 但 UI 层部分使用了 (``std::atomic``)

* 命名规则基于 Qt/WebKit 的自定义规则

  * 类名使用 ``UpperCamelCase``
  * 方法名使用 ``lowerCamelCase``
  * 常量以 k 开头，使用 ``UpperCamelCase``
  * 成员变量原则上带有 ``m_`` 前缀
  * 不适用于 protobuf 等自动生成的代码

fx9
==========================================

为编译效果而自研的库。fx9 通过效果插件被使用。

* 设置输出的着色器语言。可从以下选择：

  * GLSL
  * MSL
  * HLSL
  * SPIR-V

* 输入效果源代码
* 转换为 AST 并编译为 SPIR-V 格式

  * fx9 负责的是解析语法并转换为 AST
  * 词法分析和 AST 使用 `glslang <https://github.com/KhronosGroup/glslang>`_ 提供的功能

    * fx9 实现的是 DirectX 效果的语法解析和 AST 转换处理
    * 语法解析后端使用 `Lemon <https://www.sqlite.org/lemon.html>`_

* 启用优化时使用 `SPIRV-Tools <https://github.com/KhronosGroup/SPIRV-Tools>`_ 优化着色器
* 根据输出的着色器语言使用 `SPIRV-Cross <https://github.com/KhronosGroup/SPIRV-Cross>`_ 进行转换
* 以 fx9 自有的 protobuf 格式的二进制数据输出

  * 数据规范定义在 ``emapp/resources/protobuf/effect.proto``
  * 由于 protobuf 在 emapp 上，尚未完全分离为独立库

nanodxm
==========================================

为解析 DirectX .x 格式文本数据而自研的库。不支持二进制格式。

可以作为一个独立的库使用。

undo.c
==========================================

emapp 中使用的专注于 undo/redo 操作的自研库。
为了实现在崩溃后启动时的恢复处理，支持通过回调进行持久化。

可以作为一个独立的库使用。

sokol
==========================================

https://github.com/floooh/sokol （实际使用分叉版本 https://github.com/hkrn/sokol）

nanoem 用作渲染后端的库。

基本使用原始实现，但为了调试和读取缓冲区，会直接访问内部结构进行扩展。
此外，为了能切换多个后端，作为共享库集成。

最初使用的是 `bgfx <https://github.com/bkaradzic/bgfx/>`_，但出于以下原因进行了切换。不过相关库 bx 和 bimg 仍继续使用。

* 需要显式设置缓冲区上限
* 内部结构难以调试
* 无法直接访问后端的对象

ImGui
==========================================

https://github.com/ocornut/imgui

nanoem 用作 GUI 后端的库。

主要用作游戏开发中的 GUI 库，但在 nanoem 中直接作为用户使用的 GUI 库。
从初期就开始使用，当时使用默认外观，但曾经采用过 `nuklear <https://github.com/vurtun/nuklear>`_，
因此为了与 nuklear 的外观统一，修改了外观。

杂谈
******************************************

有打算用 Rust 重写吗？
==========================================

没有。主要基于以下原因：

* 代码库过于复杂
* Rust 与状态依赖的设计兼容性非常差
* 依赖库的问题

另一方面，基于 C 语言 API 的插件机制，插件部分已部分采用 Rust。
具体来说，目前正在开发并计划未来采用的 ``plugin_wasm`` 和未公开的新效果插件均使用 Rust 编写。

有计划推出 Android/iOS 版吗？
==========================================

没有。即使技术上可能，基于以下两点原因决定不实现：

* nanoem 的 UI 设计经过变更使其接近 MMD，并且实质上是固定尺寸设计

  * Android/iOS 以触摸操作为前提，需要为此重新设计 UI

    * 存在触摸时手会遮挡操作目标的根本问题
    * 字体尺寸较小且 UI 边距紧凑，按钮触摸操作所需尺寸不足

      * 即使是更改字体或字体尺寸也足以使 UI 发生重大变化（因此实质上是固定尺寸），实际上无法实施

  * 使用笔或鼠标可以在一定程度上操作，但既然需要它们，在 Android/iOS 上就没必要了

* MMD 只能在 Windows PC 上运行，在 Android/iOS 上运行其制作的模型视为超出使用条款范围

  * 即使能运行，多边形的数量和重量级物理运算也会导致运行缓慢或显示异常
  * Android 区分文件名大小写，因此纹理缺失问题发生概率更高

    * 这是因为 Windows 出于历史原因不区分文件名大小写，且模型作者也未能注意到这一点
    * Linux 版也存在同样问题，但根据文件系统设置可能可以缓解

MMD 能否迁移到 DirectX11？
==========================================

首先，这个问题的背景是 2021 年 1 月底，出于安全原因，Microsoft 官方页面删除了 SHA1 签名的面向最终用户的 DirectX9 安装程序及「旧版」DirectX9 SDK（`英文解说文章 <https://walbourn.github.io/where-is-the-directx-sdk-2021-edition/>`_）。本来是计划中的事项，因时势推迟，本以为不会恢复，但至少 `英文版 <https://www.microsoft.com/en-us/download/details.aspx?id=35>`_ 似乎已重新签署 SHA2 后重新发布。

由于一段时期发生了上述混乱，MMD 官方页面采取了允许直接下载可再分发的面向最终用户的 DirectX9 安装程序的措施。正因为如此，推测可能会有人提出这个问题，特此记录。

.. note::
    可能令人意外的是，DirectX9 运行时本身已包含在 Windows 10 中，并且持续维护。

    另一方面，MMD 使用的作为使用 DirectX9 的事实标准库 D3DX 不在 Windows 10 中，因此需要通过 DirectX9 安装程序引入 [#f1]_ [#f2]_。

    D3DX 因历史原因存在多个版本差异，很难正确引入，因此必须通过安装程序引入，这也是禁止单独再分发 D3DX 的依据 [#f2]_。

出于以下原因，至少本体自身可能无法迁移。另外，即使侥幸迁移成功，也可能与 DirectX9 的版本完全不同，用户是否愿意使用仍是未知数。

* DirectX9 与 DirectX11 在设计层面不同，从 DirectX9 迁移到 DirectX11 需要设计变更

  * 此外，MMD 使用 D3DX，但 DirectX11 不直接提供同等功能 [#f3]_，需要替换为自有的实现

* MME 使用的效果语法在 DirectX11 上不兼容，无法使用

  * 需要重新编写支持 DirectX11 的效果
  * DirectX 的效果格式本身已弃用，未来是否可用尚不明确

* MMD/MME 本身的开发实际上已停滞

不过，有一些通过利用 MME 机制而非 MMD 本体来支持 DirectX11 的尝试。

* MME 开发者本人尝试以相同机制支持 DirectX11

  * 视频为 `sm21860058 <https://www.nicovideo.jp/watch/sm21860058>`_
  * 可能只是尝试 DirectX11 新功能的试验性尝试，截至 2021 年 2 月似乎没有进一步进展

* 其他开发者尝试以与 MME 相同的机制支持 DirectX11

  * 视频为 `sm35941062 <https://www.nicovideo.jp/watch/sm35941062>`_
  * 以同一开发者的 MMDPlugin 机制为基础
  * 看起来也支持效果，但似乎是基于 HLSL Shader Model 5.0 应用 MME 语法的独特格式

MMD 能否迁移到 x86 以外的架构？
==========================================

如前所述，MMD 依赖于 D3DX，由于 D3DX 是闭源的，除非摆脱 D3DX 依赖或 D3DX 支持 x86 以外的架构，否则无法迁移。
DirectX9 版的 D3DX 已停止维护，甚至有推荐迁移的文章 [#f3]_，因此支持 x86 以外的架构基本无望。

至少 ARM 版可以通过 x86 模拟来应对，但从性质上速度下降不可避免，特别是物理运算可能成为瓶颈。
